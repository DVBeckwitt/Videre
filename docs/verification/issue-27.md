## Captions

The player previously loaded only the caption URL from video metadata. On
`invidious.dvbeckwitt.duckdns.org`, standard caption requests returned successful
empty bodies while the separate transcript endpoint returned usable text. On
authenticated NerdVPN, the tested transcript requests returned HTTP 500 with
`YouTube API error (code 400)` and standard caption bodies contained no usable
WebVTT cues. These failures were observed independently of the subtitle renderer.

The playback loader now tries structured transcripts, then the advertised
same-origin caption URL. If neither yields playable captions, it checks the
instance's watch page for the exact requested language/label and uses its
same-origin caption track. This last fallback is bounded to one page and one
track request; it rejects redirects and external tracks and preserves signed
query strings without logging them. Account and extraction-backend context stay
with the playing video. Access refusals do not trigger further fallback.

Observed live examples:

- DVBeckwitt: `jNQXAC9IVRw`, English manual transcript, six playable cues.
- DVBeckwitt: `M7lc1UVf-VE`, English autogenerated transcript, 572 cues.
- DVBeckwitt: both manual and autogenerated captions visibly rendered over
  playing video in the Android app.
- NerdVPN: `jNQXAC9IVRw`, authenticated watch-page companion tracks, six English
  and four German manual cues. The signed track addresses are deliberately not
  retained here.
- NerdVPN: `9bZkp7q19f0`, Korean autogenerated captions visibly rendered over
  playing video in the Android app. The actual player recovered from a failing
  transcript request through the standard-caption and watch-page fallback.
- NerdVPN: the `M7lc1UVf-VE` watch page also returned HTTP 500 during testing.
  Caption recovery cannot promise availability when the server's routes all fail.
- NerdVPN: on the routing APK, `M7lc1UVf-VE` played with **Proxy videos on**
  and **Network proxy off**. Its non-autogenerated English track visibly
  rendered over advancing video, using the transcript-to-caption-to-watch
  fallback. This final native check supersedes the earlier manual-display
  limitation. The `jNQXAC9IVRw` metadata request still failed during that check;
  server availability remains video-dependent.

The autogenerated sample contained 566 intervals of exactly 10 milliseconds.
For structured transcripts explicitly marked autogenerated, the conversion
extends such a marker to the next valid cue's start when that start is later.
This is a display inference from observed upstream data. Manual timing, longer
autogenerated intervals, and the final cue's supplied end remain unchanged.
Repeated timed lines are preserved; headings and invalid intervals are excluded.

Upstream describes its separate transcript-to-WebVTT path as a timedtext
workaround in [the transcript implementation](https://github.com/iv-org/invidious/blob/master/src/invidious/videos/transcript.cr).

## Music

The default catalog now uses standard Invidious search, channels, trending,
playlists, and mixes. The old direct-catalog implementation is not instantiated
by the application. Saved Google artwork uses the existing Invidious image
proxy, including notification and download covers. Album bookmarks remain saved;
the UI explains that standard Invidious cannot resolve YouTube Music album IDs.

Live source checks using the app's service, HTTP overrides, and default catalog
returned 20 songs, 20 channels, 20 playlists, and 15 trending tracks from
DVBeckwitt. All six requests in that check stayed on the selected instance.
Authenticated Android Music search and artwork also loaded on both NerdVPN and
DVBeckwitt. NerdVPN's observed API calls were `/api/v1/trending` and
`/api/v1/search`; this log check is not a packet capture. Installing the final
debug APK retained the encrypted NerdVPN login, and Music search and artwork
loaded again on that APK.

On the final alias APK, DVBeckwitt Music Songs search selected officialpsy's
`9bZkp7q19f0`, confirmed by the instance's video-metadata request. Audio visibly
advanced from 00:09 to 00:29, and Pause worked. This check used Proxy videos on
and Network proxy off. The emulator was then returned to the saved public
NerdVPN account, with its encrypted login retained and Music Home visible.

Playlist regressions cover Invidious's overlapping page windows, missing and
filtered entries, repeated recordings at distinct source indices, and native
`RD` mix responses. Neither duplicated page entries nor filtered overlap counts
can cause a playlist to finish early.

Audio playback was checked separately from catalog availability. The routing
investigation loaded the metadata and artwork for the displayed Get Lucky
official-audio item, but
the Android audio player received HTTP 403 and remained at position zero with
both Network proxy and Proxy videos off. The collaborating task reproduced the
same failure class through Tor with Proxy videos off. The direct UI test recorded
a requested ID rather than independently confirming the selected upload's ID;
it should not be treated as an exact-upload comparison with the separate
`4D7u5KF7SP8` Topic-track probe. These observations do not establish the cause,
but show that stream failures are not confined to Tor.
Catalog success is not evidence that every returned media stream plays.

The proxied path exposed a separate routing defect: Videre replaced the media
hostname with the selected instance but omitted Invidious's required `host`
query parameter. A controlled request through NerdVPN over Tor changed from
HTTP 400 (`Invalid hostname.`) to HTTP 206 with 1,024 audio bytes when that
parameter was supplied. The shared media helper now retains the original host
while preserving signed query spelling, order, and duplicate fields. Existing
same-origin URLs and direct mode remain unchanged. Music prefers an available
audio-only stream even when Proxy videos is on; the tested combined stream
still returned HTTP 403. Downloads also use the shared media proxy routing.

The authenticated NerdVPN onion API also returned media URLs using its public
hostname. The helper now maps recognized media paths between the exact known
NerdVPN origins back to the selected endpoint, preserving the signed query and
original Google media host. It rejects lookalike hosts, user information,
unexpected ports, traversal, and unrelated paths. A final native onion check
admitted the selected onion's audio source and played the `M7lc1UVf-VE` tutorial
audio, including in the background. This is audio-route evidence, not a
music-catalog song result.

The final native Tor song check then selected PSY `9bZkp7q19f0` from Music Songs
search. Its actual audio position advanced from 4.013 to 17.426 seconds before
Pause, with the engine ready and no terminal error. The source used the exact
selected HTTP onion endpoint, audio itag 251, and the original media hostname.
After background playback, the paused position reached 24.130 seconds. This
establishes Music-catalog song and background playback through Tor. The official Get
Lucky upload `5NV6Rdv1a3I` still returned HTTP 403 on the correctly routed source;
both tested audio encodings were refused. That track remains unavailable in
the tested configuration.

A separate audio-only download of `M7lc1UVf-VE` through the onion advanced from
1% to 5%. The task-created download was then removed and the download manager

The separate Tor test account and its saved key were removed, the original
settings were restored, and task-owned transport/emulator processes were
stopped. The user's sign-in emulator remains open with the public NerdVPN
account logged in, Proxy videos on, Network proxy off, and Music Home visible.

A supplemental public-NerdVPN video-to-audio toggle test also played the
tutorial audio and continued in the background, advancing from 855.555 to
872.676 seconds. That toggle initially left a stale video surface; backing out
exposed the working audio mini-player. This separate UI observation was not
part of the Music Songs search path tested above.

The same checks exposed a separate client defect: pressing Play after a terminal
audio failure could report Playing while the native player remained idle at
position zero. Terminal failures now pause the player and preserve the error;
late callbacks cannot replace it. Play reloads the source through the normal
admission path, or asks the parent player to fetch full metadata if the previous
request left only a search result. Focused regressions cover retry, stale events,
position, speed, pitch, and pause behavior. Repeated Play while admission is
pending cannot announce Playing, and a Pause command during metadata loading
remains effective when the hydrated source arrives.

## Backend startup retry

The collaborating task added one bounded retry for NerdVPN's exact temporary
backend-startup error. It preserves the selected account and backend, honors a
short Retry-After within the request budget, and cancels if the active selection
changes. It does not retry arbitrary server errors or guarantee upstream video
availability. Its 33 regression tests are included in the canonical test run.
